# HACS 共通鍵による変換秘匿仕様案 v1

状態: 日本時刻00:00の自動更新、16音／32音の鍵付き変換、共有ストアの共通鍵管理・即時更新を実装済み。旧版の固定鍵付き割当案に加え、以下の期間鍵導出方式を使用する。実機コードの自動更新・別ホスト間の鍵配布は未実装。

## 目的と保護範囲

呼び出し相手先と呼び出しコードの固定された公開対応を、共通鍵ごとに異なる対応へ変更する。SELCALの4文字規則・周波数・信号時間を維持し、既存のコード設定可能な受信装置に同じコードを設定できるようにする。

これは**鍵付き対応付け**であり、SELCAL音声や音声通話の暗号化ではない。標準の暗号化方式や認証済み暗号装置として扱わない。音声だけでは鍵の一致、送信元の真正性、再送でないことを確認できない。

## 共通鍵の強度

| 項目 | 設計値 |
|---|---|
| 共通鍵 | 256ビット（32バイト） |
| 生成 | OSの暗号学的乱数源。Pythonなら `secrets.token_bytes(32)` |
| 保存形式 | 64桁の16進文字列。ただし64桁であるだけでは256ビットのエントロピーを保証しない |
| パスワード入力 | 採用しない。人が作った文字列や呼び出し相手先を鍵に使わない |
| 鍵の範囲 | 同じ対応を使う送信部・受信シミュレータで共有 |
| 鍵の公開 | Git、Dockerイメージ、API、画面、WAV、ログに含めない |

256ビットは鍵長であり、本方式全体が256ビット相当の秘匿強度を持つという意味ではない。4桁の呼び出し相手先の空間は10000通り、約13.3ビットしかない。鍵が長くても、変換APIへの全件照会や既知の呼び出し相手先とコードの観測によって対応表は判明し得る。鍵付き変換を強い通信秘匿の代替にしない。

## 基礎となる鍵付き割当規則

HMAC-SHA-256を鍵付きの順位生成に用いる。HMACそのものはメッセージ認証用の仕組みであり、暗号化方式ではない。本設計ではHMAC値を送信せず、コードの割当順位の生成だけに利用する。従って送信音声に認証機能は付かない。

1. 呼び出し相手先 `0000`〜`9999` をすべて列挙する。
2. 各呼び出し相手先に対して、共通鍵Kで `HMAC-SHA-256(K, domain || ASCII呼び出し相手先)` を計算する。
3. 256ビットの出力全体を符号なしバイト列として昇順に並べる。同値の場合だけ呼び出し相手先の数値順を使う。
4. 並べた呼び出し相手先の位置0〜9999を、対応する基礎変換のコード位置0〜9999へ割り当てる。
5. 逆変換では基礎変換で得た位置を用いて、並べた呼び出し相手先を読み出す。

domainは方式別の固定ASCIIバイト列とし、末尾にNULを含める。

| 鍵付き変換バージョン | domain | 基礎変換 |
|---|---|---|
| HACS-KTN16-v1 | `HACS-KTN16-v1` + NUL | HACS-TN16-v1 |
| HACS-KTN32-v1 | `HACS-KTN32-v1` + NUL | HACS-TN32-v1 |

HMAC値を10000で割った余りだけでコードを選ぶ方法は使わない。全呼び出し相手先の順位を付けるので、HMAC値の同値があっても一意性を維持できる。送受信は同一の鍵、方式、変換バージョンを使う。異なる鍵で同じコードが別の呼び出し相手先に変換されることがあり、間違った鍵を音声だけで検出することはできない。

既存のHACS-TN16-v1の定義は変更しない。鍵なしモードと鍵付きモードは明示的に切り替える。鍵付きモードで鍵が未設定・不正なら起動または変換を拒否し、鍵なしモードへ自動的に戻さない。

## 受信設定と表示

送信画面には鍵付き変換で得た「受信側に設定するコード」を表示する。受信画面には同じ共通鍵から得た自機コードを表示する。共通鍵は画面から入力せず、サーバー側で乱数生成する。管理操作には共通鍵と別の管理トークンを使う。画面には変換方式、変換バージョン、管理者が付けた鍵識別名だけを表示する。

従来の実受信装置には共通鍵を持たせる必要はなく、生成された4文字コードを設定する。鍵を変更すると各呼び出し相手先のコードが変わり得るため、受信装置のコードも同時に更新する。既存航空機の登録コードを変更せず呼び出す場合は、独自の鍵付き変換ではなく確認済み実コードの対応表を使用する。

## 鍵管理と限界

Docker構成では共通鍵を共有SQLiteストアで管理し、送信部は書込み、受信部は読取り専用とする。管理トークンはDocker secretから読み込み、いずれもGit・イメージには入れない。別ホストの鍵配布は自動化していない。鍵識別子の一致は送信元の認証ではない。紛失時のため共有鍵ストアを安全にバックアップする。

呼び出しコードは音声として観測可能で、同じコードの再送を既存SELCAL受信装置は区別できない。固定対応は同じ相手の呼び出しを追跡され得る。変換APIは対応表を問い合わせられる入口になるため、利用者の認証・権限と照会制御が必要。現行のローカルHTTPサービスにはその認証機能を実装していない。

強い機密性、送信元認証、リプレイ防止が必要なら、nonceや認証タグを持つ別の暗号化プロトコルが必要であり、従来SELCAL音声のみの互換性の範囲には収まらない。

## 日・週・月の更新頻度比較

前提は、各期間で独立した新しい256ビット乱数鍵へ置き換え、旧鍵を有効な送受信に使用しないこと。更新頻度によって鍵長や基礎アルゴリズムの強度が変わることはない。以下はHACSの固定対応表についての設計上の比較であり、暗号強度を数値評価した結果ではない。

| 比較項目 | 日次 | 週次 | 月次 |
|---|---|---|---|
| 鍵長 | 256ビット | 256ビット | 256ビット |
| 同じ対応表を使う期間 | 1日 | 7日 | 暦月の28〜31日 |
| 期間内に蓄積される観測 | 少ない | 中間 | 多い |
| 受信設定コードの更新負担 | 毎日 | 毎週 | 毎月 |
| 更新・同期に失敗する機会 | 多い | 中間 | 少ない |
| 運用上の適用案 | 自動更新・同期が可能 | 手動更新を含む運用 | 更新困難な試験・低頻度利用 |

観測の比較は同じ呼び出し頻度を前提とする。1日あたりr回なら、同じ対応表を使う観測機会は概ねr、7r、28r〜31r。ただし、同じ機体の反復呼び出しは新しい対応関係を増やさず、更新前後の機体を他の情報から追跡できる場合もある。日次が週次の7倍、月次の30倍の暗号強度になるという意味ではない。

短い周期は現行対応表の有効期間を短縮できるが、すでに判明した過去の対応を秘密に戻すことはできない。攻撃者が継続して鍵や変換APIへアクセスできる場合、周期だけでは解決しない。例えば毎秒q件の呼び出し相手先を照会できるなら、全10000入力の対応取得に要する時間は約10000/q秒であり、鍵の総当たりは不要。SELCAL 32であっても入力4桁・10000通りというこの制約は変わらない。

親鍵から日時だけを使って期間鍵を再生成する方式では、親鍵の漏えいが複数期間へ及ぶ。周期の比較で独立鍵と同じ漏えい封じ込めを仮定しない。漏えいが疑われたら次の予定更新を待たず、鍵と対応表を失効させる。

更新周期を導入する際は、送受信共通の切替時刻・タイムゾーン・期間識別名を設定する。期間識別名はSELCAL音声には入らない。WAVの保存試験は生成時の期間を明示して判定し、現在時刻だけで別の期間鍵を適用しない。従来受信装置の固定コードも各周期で更新する必要がある。旧・新コードの併用は有効期間を延ばすため別途評価する。

### 更新時刻（確定）

更新時刻は**日本標準時（JST、UTC+09:00）の00:00:00**とする。ホストOS、Dockerコンテナ、ブラウザのローカルタイムゾーンによらず、JSTで期間を判定する。16音／32音の両方に適用する。

| 更新周期 | 切替日時 | 期間識別名の例 |
|---|---|---|
| 日次 | 毎日00:00 JST | `D-2026-10-12` |
| 週次 | 毎週月曜日00:00 JST（基準曜日） | `W-2026-10-12`（開始した月曜日の日付） |
| 月次 | 毎月1日00:00 JST | `M-2026-11` |

週次の基準曜日は月曜日、月次の基準日は1日を既定とする。日次／週次／月次のどの周期を使うかは別設定であり、更新時刻の確定だけで日次を自動的に選択しない。

各期間の開始を含み、次の開始を含まない半開区間で判定する。例: 日次では2026-10-11 23:59:59 JSTまで旧期間、2026-10-12 00:00:00 JSTから新期間。JSTの00:00はUTCでは前日の15:00となる。週・月はJSTの暦で計算し、週番号や一律30日間の加算で代用しない。

送受信は時刻を同期し、周期と期間識別名を一致させる。有効な共通鍵ストアを読み込めない場合は変換と新規呼び出しを停止し、旧鍵や鍵なし変換で代替しない。切替後の新規呼び出しに、前期間で生成・保存されたコードやWAVをそのまま使用しない。再起動時も現在のJST期間で選び、起動時刻から24時間後などを基準にしない。通信途中の切替と旧期間WAVの検証手順は実装時に別途扱い、通常呼び出しへ旧鍵を自動的に併用しない。

更新判定はサーバーのタイムゾーン付き現在時刻から処理ごとに行う。常駐タイマーやcronの実行遅延に依存せず、新期間の最初の処理から新しい対応表になる。画面は次回切替時刻と定期ポーリングで更新を確認し、再生・保存の直前にもサーバーへ確認する。

HACSの設計判断として、自動更新・同期と受信コードの更新が可能なら日次を候補とする。手動更新が必要なら週次が運用負担との折衷案。月次は変更回数を減らせるが、対応の観測蓄積が増える。いずれも強い通信秘匿、送信元認証、リプレイ防止を保証しない。自動更新は次節の期間鍵導出方式で実装済み。独立した共通鍵を毎期間配布する方式とは漏えい時の影響範囲が異なる。

## 実装した自動更新と共通鍵管理

`rotation.py` は32バイトの親鍵から `HMAC-SHA-256(root, ASCII("HACS-period-v1") || NUL || ASCII(期間ID))` で期間鍵を導出し、前記順位生成へ適用する。バージョンは `HACS-RKTN16-v1`／`HACS-RKTN32-v1`。同じ親鍵・周期・期間・方式なら別プロセスで同じ対応表になる。日次／週次／月次で変更するのは期間鍵と対応表であり、親鍵は自動的に交換しない。親鍵漏えいはその親鍵から導出される他の期間にも及ぶ。

`compose.rotation.yaml` の初回起動では送信部が新しい親鍵を生成し、共有鍵ストアへ保存する。受信部は共有ストアを読む。既存ストアの破損時は停止し、勝手な再生成や鍵なしへの復帰をしない。ストアを失うと鍵と設定コードを復元できない。

送信画面の「共通鍵の管理」で、管理トークンを入力して即時更新できる。新しい独立した256ビット親鍵を生成して有効鍵をトランザクションで入れ替え、旧鍵を通常処理に使わない。更新前の鍵識別子が一致する場合だけ更新し、二重操作を防ぐ。履歴には世代、識別子、日時、理由だけを残し、旧鍵そのものをアプリから復元する機能は持たない。ディスクやバックアップからの物理的消去を保証するものではない。

各処理は鍵と期間のスナップショットを使う。共通鍵の更新は同日内でもコードを変更し得るため、期間IDだけでなく鍵識別子も画面・要求・応答で照合する。ブラウザは更新時に旧音声を無効化し、再生・保存の直前にも照合する。更新時刻に再生がかからないよう、再生時間＋0.25秒未満で切替を迎える場合は新しい再生を拒否する。処理開始済みの要求は以前のスナップショットを使うことがあるが、生成後の画面確認で旧音声を再生対象にしない。

鍵付きWAVには音声を変えないRIFF追加チャンクとして期間IDと鍵識別子を保存する。受信シミュレータは失効鍵や別期間のファイルを拒否する。過去のWAVは「生成期間」を明示すると現在の親鍵から過去期間を導出して試験できる。親鍵を更新した後の旧鍵WAVは拒否し、旧鍵を自動復活させない。この付加情報は署名されておらず、RFに送信する情報でもない。呼び出し検出は引き続きPCM音声から行う。

管理トークンは鍵と別の32バイト乱数値。管理APIはBearerトークンを要求し、画面はトークンをブラウザに永続保存しない。変更APIでは同一OriginとJSON形式も確認する。ローカル端末からの利用を前提とし、インターネット公開・LAN向けの利用者認証は追加していない。変換APIの全件照会という既述の限界は残る。

実受信装置は新しい4文字コードへ別途設定し直す必要がある。別環境の受信シミュレータは安全に同じ鍵を配布しなければ同期しない。共有ボリュームを使う同一Docker環境の2サービスが今回の自動反映対象。

起動手順は[自動更新・鍵管理・プリセットの操作説明](automatic-rotation-and-management.md)を参照。

## 受入条件

- 全10000呼び出し相手先の有効コード生成、一意性、逆変換一致、先頭ゼロ保持。
- 同一鍵・方式・バージョンで別プロセス／各OSの結果が一致。
- 異なる鍵の対応表が異なること、鍵なしの既存結果が変わらないこと。
- 未設定鍵、不正長、不正16進、未割当コードを拒否し、鍵なしへ自動復帰しないこと。
- 画面・API・ヘッダ・ログ・例外・Git・イメージに鍵を出さないこと。
- 鍵変更時の受信設定更新と、異鍵での誤った呼び出し相手先復元の扱いを確認。

## 根拠と位置付け

- NIST: [SP 800-57 Part 1 Rev.5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final)、5.3節 — 鍵の使用期間はアルゴリズム、使用量、露出リスク、漏えい時の影響、鍵交換の負担などで決める。HACSの日次・週次・月次の比較は、この一般原則を用いた設計判断であり、NISTがHACSに周期を指定したものではない。

- NIST: [FIPS 198-1 HMAC](https://csrc.nist.gov/pubs/fips/198-1/final) — HMACは鍵付きハッシュによるメッセージ認証の仕組み。
- NIST: [SP 800-38G Rev.1 第2公開草案](https://csrc.nist.gov/pubs/sp/800/38/g/r1/2pd) — 2025年の草案はFF1の最小ドメインを100万へ引き上げる。4桁10000通りにFF1を適用して、この草案に適合した強い暗号化と称する設計にはしない。

本書の順位生成による対応付けはHACS独自の対応付け方式であり、NIST承認の形式保持暗号ではない。第三者による安全性評価は未実施。
