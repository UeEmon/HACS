# HACS 二方式対応仕様 v1

仕様状態: 16音／32音の変換・音声生成・WAV受信・API・方式選択を実装済み。登録コード対応表、画面の全再構成、実機・各OSの動作検証は未完了。

## 対象

HACSの送信音声生成とWAV受信シミュレータを、従来16音とSELCAL 32の両方に対応させる。4桁の呼び出し相手先入力、Windows・Mac・Linux共通のDocker構成、Git管理を維持する。接続先はメーカーを限定しないHF無線機とする。コード変換・信号生成は共通化し、音声・PTT接続は機種別アダプタで対応する設計とする。[汎用音声入力・PTTテンプレート](generic-radio-interface.md)としてプロファイル・ドライバ契約・ドライランを用意する。ホスト音声・RTS/DTRの汎用ドライバを実装する。Ethernet・1553・シリアルデータ制御は追加検討対象とし、機種別の接続仕様確定・専用ドライバ・実機試験は引き続き保留する。

## 方式と共通信号

| 項目 | `selcal16` | `selcal32` |
|---|---|---|
| 使用音数 | 16 | 従来16音＋追加16音 |
| 使用文字 | `ABCDEFGHJKLMPQRS` | `ABCDEFGHJKLMPQRSTUVWXYZ123456789` |
| 表示形式 | `XX-YY` | `XX-YY` |
| 音声 | 第1組の2音を同時出力→無音→第2組の2音を同時出力 | 同左 |
| 生成時間 | 1.0秒／0.2秒／1.0秒 | 同左 |
| WAV | 48 kHz・16 bit・mono・2.2秒 | 同左 |
| 自動変換 | `HACS-TN16-v1` | `HACS-TN32-v1`（本書で定義） |
| 初期選択 | 既存設定を継承。設定なしはこの方式 | 明示的に選択 |

4文字はすべて異なる文字とする。各組内は上表の明示的な文字順位で昇順とし、第1組と第2組の順序は交換しない。数字は文字の後に配置する。ASCII順、周波数順、ロケールのソートは使わない。例えば32音の `D3-A5` は有効、`3D-A5` は無効。`0`、`I`、`N`、`O` はいずれの方式でも使用しない。入力の大文字化とハイフン補完は可能だが、組内の並べ替えはせず入力エラーを表示する。

2音は同一振幅で合成し、合成ピーク上限を出力レベルとする。現行の0.01〜0.9を維持する。時間の公開仕様上の許容値は各組1.0±0.25秒、間隔0.2±0.1秒。生成時は公称値を使う。出力レベルはPCM振幅であり、無線機入力電圧やRF変調度ではない。

## 呼び出し相手先とコード

呼び出し相手先はASCII数字4桁の文字列 `0000`〜`9999` とし、先頭ゼロを保持する。数字を1文字ずつ音文字に置換せず、呼び出し相手先全体から有効なコードを選ぶ。

### 既存の16音変換

`HACS-TN16-v1` の列挙規則・対応結果を変更しない。[呼び出し相手先変換アルゴリズム](tail-number-mapping.md)を引き続き使用する。

### 32音変換 HACS-TN32-v1

1. 文字順位を `ABCDEFGHJKLMPQRSTUVWXYZ123456789` に固定する。
2. 第1組を32文字から2文字の組合せとして文字順位の辞書順に列挙する。
3. 各第1組について、使用済み2文字を除いた30文字から第2組を同じ規則で列挙する。
4. 4文字すべてが従来16文字に含まれるコードを除外する。残った順序を保持する。
5. 残った列の先頭10000コードに呼び出し相手先0000〜9999を順に割り当てる。

逆変換はこの列の位置を求め、0〜9999だけを4桁文字列に戻す。残りは未割当として扱う。コード空間は計算上 `C(32,2)×C(30,2)=215760`、従来コードを除いた列は `215760−10920=204840` 通り。これはHACSの列挙可能数であり、ASRIによる実際の登録可能数や割当数ではない。

| 呼び出し相手先 | HACS-TN16-v1 | HACS-TN32-v1 |
|---|---|---|
| 0000 | AB-CD | AB-CT |
| 0001 | AB-CE | AB-CU |
| 5501 | EM-DL | AT-U7 |
| 9999 | LS-JR | A5-C7 |

32音の自動変換結果は追加音を最低1音含むため、16音変換の結果と衝突しない。方式を変更すると同じ呼び出し相手先のコードも変わるので、画面で変換結果を更新し、生成済みWAVを無効化する。送受信で変換バージョンを合わせる。バージョンや呼び出し相手先を音声に追加送信しない。

### 実機に設定されたコード

独自変換はシミュレータ用の対応規則であり、既存航空機の登録コードとの一致を意味しない。将来の実機向けには、呼び出し相手先と確認済み実コードの対応表を使う別の `registered` 指定を設ける。未登録呼び出し相手先を独自変換へ自動的に切り替えない。対応表のコードは選択方式の検証を受ける。32音方式で従来16音だけの実コードを指定することも可能とする。

## 操作・API・設定

送信画面に方式選択、呼び出し相手先、変換バージョン、生成コードを表示する。受信画面は受信能力（16音／32音）、自機番号、自機の変換方式を分けて表示する。32音受信能力なら16音・32音のどちらを自機の変換方式に選んでもよい。16音受信能力に32音の自機変換は設定できない。方式選択は各画面のブラウザに保存し、WAVの方式・コードを画面とダウンロード名で確認できるようにする。

以下は実装済みのインターフェース。既存URLで `mode` を省略した場合は `selcal16` とし、既存利用者の結果を変えない。

| インターフェース | 指定例 |
|---|---|
| 順変換 | `/api/convert?tail_number=5501&mode=selcal32` |
| 逆変換 | `/api/convert?code=AT-U7&mode=selcal32` |
| WAV生成 | `/tone.wav?tail_number=5501&mode=selcal32` |
| 直接コードのWAV生成 | `/tone.wav?code=D3-A5&mode=selcal32` |
| 受信判定 | `POST /api/decode?own_tail_number=5501&mode=selcal32&own_mode=selcal32` |
| CLI | `python3 selcal.py --tail 5501 --mode selcal32 --output HACS-5501-selcal32.wav` |

受信APIの `mode` は受信能力、`own_mode` は自機番号の変換方式を表す。`own_mode` 省略時は `mode` と同じとする。既存の `own_code` による直接設定も維持する。送信側の `tail_number` と `code`、受信側の `own_tail_number` と `own_code` はそれぞれ同時指定を拒否する。不明な方式、対応外文字、不正コードはHTTP 400とし、方式を推測して黙って補正しない。

変換APIは `mode`、`mapping_version`、`tail_number`、`selcal_code` を返す。直接コード指定時は割当元を明示し、呼び出し相手先の逆変換を確実な実機識別として表示しない。WAV応答ヘッダは既存コード・変換バージョンに加え `X-HACS-Mode` を返す。PCMだけを読み込む受信部はヘッダやファイル名に依存しない。

## 受信シミュレータと互換性

| 送信されたコード | 16音の受信能力 | 32音の受信能力 |
|---|---|---|
| 従来16音だけのコード | 検出対象 | 検出対象 |
| 追加音を含むコード | 呼び出し対象外 | 検出対象 |

32音受信部は全32音を解析し、従来コードを除外しない。従来音だけのWAVから「16音設定で生成したか32音設定で生成したか」を判別することはできない。追加音の有無は検出できるが、実機コードの割当元や呼び出し相手先は音声だけでは確定しない。

自局一致は検出コードと自機設定コードで判定する。`alert`、`other_station`、`not_detected` を維持し、検出コード、追加音の有無、HACS逆変換候補を別項目で返す。32音受信部はコード内容に応じてTN16またはTN32を逆変換し、割当範囲外は呼び出し相手先をnullとする。16音受信部が追加音の信号を検出できない場合は `not_detected` とし、追加音を従来音に置換しない。

32音では100 ms解析窓にHann窓と振幅補正を追加して周波数漏れを抑える。32音では最小周波数間隔が16.6 Hzになり、16音時の34.1 Hzより狭い。窓長、周波数誤差、音対の分離、タイミング判定を評価し、誤ったコードで自局通知しないことを優先する。解析入力の上限（PCM WAV、8〜96 kHz、16 bit、mono、10秒、2 MB）は維持する。

## 構成と受入条件

送信コンテナと受信シミュレータの2コンテナ構成、ポート8787・8788を維持する。音声出力は各OSのブラウザから行う。方式ごとの音文字・周波数・文字順位は共通の固定プロファイルとして管理し、コード検証、変換、送信、受信が同じ定義を参照する。移行で既存APIの既定値とTN16の結果を変えない。

実装完了条件:

- 既存16音の試験がすべて通り、全10000呼び出し相手先の変換結果が変更されない。
- TN32の全10000入力について有効性、一意性、逆変換一致、追加音の含有、TN16との非衝突を確認する。
- 全32音の周波数・成分レベル、1.0秒／0.2秒／1.0秒、PCM仕様を独立した基準値で確認する。
- 英字と数字の組内順序、重複文字、0・I・N・O、不明方式、未割当コードを確認する。
- 両方式の呼び出し相手先→WAV→受信→自局通知／他局表示を確認する。32音受信で従来コードも確認する。
- 隣接音、時間境界、周波数誤差、雑音を含む音声で誤通知と未検出を評価し、試験条件・限界を記録する。
- Docker起動とブラウザ操作をWindows・Mac・Linuxで確認する。実機相互接続・RF測定は別段階とする。

## 今回の検証結果

既存18試験と32音向け5試験が合格。TN32全10000入力の一意性・逆変換・TN16非衝突、全496音対の44.1 kHz／位相差／+0.15%周波数偏差の判定、代表コードのWAV検出、32音受信による従来コード検出、両方式のHTTP一連処理を確認。雑音・フェージング・負の周波数偏差・任意の開始位置の網羅評価と実機試験は未実施。
